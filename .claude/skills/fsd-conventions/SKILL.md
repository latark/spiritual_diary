# Архитектура: Feature-Sliced Design

Кодовая база уже консистентна. Задача не в том, чтобы сделать по теории FSD, а чтобы
**совпасть с тем, что уже есть**. Перед новым кодом посмотри на ближайший аналог в
`src/features/` и повтори его форму. Этот скилл фиксирует сложившиеся паттерны, чтобы
они не плыли.

## Слои и направление зависимостей

Порядок сверху вниз. Зависеть можно **только вниз**:

```
app → views → widgets → features → entities → shared
```

- `app/` — Next.js routing и layouts. **Минимум логики**: auth-гейт, fetch для server
  component, композиция виджетов. Бизнес-логике тут не место, она в слое ниже.
- `views/` — FSD pages-слой (имя `views`, т.к. Next занял `pages/`). Сборка экрана.
- `widgets/` — крупные самостоятельные блоки (`app-shell`).
- `features/` — пользовательские фичи (`emotion-record`, `auth`, `onboarding`, `emotion-wheel`).
- `entities/` — бизнес-сущности (пока пусто, заполняем по мере надобности).
- `shared/` — переиспользуемое без доменной привязки: `ui/`, `lib/`, `config/`, `api/`,
  `content/`, `safety/`, `styles/`.

**Нельзя:** `shared` импортирует из `features`; `feature` импортирует из `views`;
два feature импортируют друг друга напрямую. Если две фичи делят код, он спускается
в `shared` или `entities`. Если код тянет вверх, значит ты ошибся слоем.

## Импорты

- Между слоями — **только абсолютные** `@/shared/...`, `@/features/...` (`@/*` настроен
  в tsconfig). Никаких `../../../`.
- Импортируй слайс **через его public API** (`@/features/emotion-record`), а не глубоким
  путём в потроха (`@/features/emotion-record/model/valence`). Глубокий импорт — это
  сигнал, что нужное не вынесено в `index.ts` либо что код лежит не в том слайсе.
- Внутри слайса между его файлами — относительные (`./entry-schema`, `../model/types`),
  как в `save-action.ts`.

## Public API слайса — `index.ts`

Каждый слайс обнародует только нужное наружу. Реэкспорт точечный, а не «всё подряд».
Эталон (`features/emotion-record/index.ts`):

```typescript
export { BodyMap } from './ui/BodyMap';
export { RecordSteps } from './ui/RecordSteps';
export { familyValence, type Valence } from './model/valence';
export { BODY_ZONES, BODY_ZONE_BY_ID, type BodyZone } from './model/body-zones';
export type { RecordEmotion } from './model/types';
```

Добавил новый публичный компонент или тип — допиши строку в `index.ts`. Внутреннее
(хелперы, под-компоненты шагов) наружу не выводим.

## Анатомия слайса

```
features/<slice>/
  index.ts            public API (точечные реэкспорты)
  model/              логика, данные, без JSX
    types.ts          интерфейсы сущности слайса
    <name>-schema.ts  Zod-схема + inferred-тип (z.infer)
    <name>-action.ts  server action ('use server') — см. скилл server-action
    <name>.ts         чистые функции/константы (valence.ts, chakra.ts, body-zones.ts)
  ui/                 React-компоненты (PascalCase.tsx)
```

- В простом слайсе меньше файлов. Не плоди пустые папки ради симметрии.
- `model/` не содержит JSX. `ui/` не содержит бизнес-логики и прямых запросов к БД,
  данные приходят пропсами от server component.

## Нейминг

- Папки и не-компонентные файлы — **kebab-case** (`emotion-record`, `body-zones.ts`).
- React-компоненты — **PascalCase.tsx**, один компонент на файл (`RecordSteps.tsx`).
- Хуки — `useThing.ts` с префиксом `use`.
- Экспорты — **named** по умолчанию. `default` только там, где требует Next.js:
  `page.tsx`, `layout.tsx`, `route.ts`.

## Server / Client Components

Server Component — **по умолчанию** (страницы, layouts). `'use client'` ставь на
**самом узком** уровне и только под интерактивность (state, обработчики, анимации,
`useFormStatus`/`useActionState`).

- **Данные грузит server-компонент** (`createSupabaseServerClient()` + запрос),
  результат отдаёт client-компоненту пропсами. Эталон — `app/(main)/page.tsx`.
- **Client-компонент не фетчит сам**, никаких `useEffect`-загрузок. Он про state и UI.
- Не вешай `'use client'` на страницу целиком, чтобы «было проще». Так весь рендер
  утаскивается на клиент, и разделение ломается.

## Куда положить новый код — решающее дерево

1. **Это маршрут/экран?** → файл в `app/(group)/route/`, внутри — только композиция и
   серверный fetch; экранную сборку выноси в `views/`.
2. **Доменная пользовательская фича** (запись эмоции, онбординг, авторизация)? → `features/`.
3. **Крупный переиспользуемый блок шела/каркаса**? → `widgets/`.
4. **Бизнес-сущность, нужная нескольким фичам** (эмоция, профиль, подписка)? → `entities/`.
5. **Без доменной привязки** (Button, cn, env, supabase-клиент, контент-справочники,
   crisis-детектор)? → `shared/` в подходящую папку (`ui/lib/config/api/content/safety`).

Сомневаешься между `feature` и `shared` — спроси: «это знает про конкретный
пользовательский сценарий?» Да → feature. Нет, переиспользуемо везде → shared.

## Частые нарушения (ловить и в своём коде, и в ревью)

- Импорт «снизу вверх» (`shared` тянет из `features`, `feature` из `views`).
- Глубокий импорт в обход `index.ts`.
- Бизнес-логика или запрос к Supabase прямо в `app/` вместо `features`/server-action.
- `'use client'` на верхнем уровне страницы без нужды.
- Новый публичный компонент не добавлен в `index.ts` (его импортируют глубоким путём).
- Относительные `../../../` между слоями вместо `@/*`.
- JSX в `model/` или fetch в `ui/`.

## Самопроверка перед сдачей

- Зависимости идут только вниз по слоям? Нет импортов вверх и между фичами напрямую?
- Чужой слайс импортирован через `index.ts`, а свой публичный API дополнен?
- Server-by-default соблюдён, `'use client'` на узком уровне, данные грузит server?
- Нейминг (kebab/PascalCase), named-экспорты, `model`/`ui` разделение на месте?
- Новый код лёг в слой, который отвечает «решающему дереву», а не «куда ближе»?

Связанные скиллы: `server-action` (паттерн мутаций в `model/*-action.ts`),
`supabase-migration` (схема/RLS под запросы), `spiritual-voice` (любой UI-текст).
